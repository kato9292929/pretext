x402とは

HTTP 402 "Payment Required" ステータスコードは、1997年から予約されていましたが、30年近く未使用のままでした。

Coinbase、Cloudflare、Stripeが主導し、Linux Foundation傘下のx402 Foundationとして設立されたこのオープンスタンダードは、ウェブリクエストに支払いを直接組み込む普遍的な方法を定義します。製品ではなく、プラットフォームでもなく—公共財です。

サーバーが402を返したとき、クライアント（人間でもAIエージェントでも）は自動的に支払いを完了し、リクエストを再試行します。人間が毎回フォームを入力する必要はありません。

仕様を読む →
HTTP Flow 
→ GET /api/data HTTP/1.1
  Host: api.example.com

← HTTP/1.1 402 Payment Required
  X-Payment-Required: version=1
  X-Payment-Amount: 0.001
  X-Payment-Token: USDC

→ GET /api/data HTTP/1.1
  X-Payment: <signed_payload>

← HTTP/1.1 200 OK
  Content-Type: application/json

x402の本領：APIエコノミーの配管

x402が実際に使われているのは、ほぼすべてが「ソフトウェアがソフトウェアのサービスを買う」ユースケースです。

  • APIコール・データ取得の従量課金
  • LLM推論のトークン単位課金
  • スクレイピングAPIのリクエスト単位課金
  • ヘッドレスブラウザのセッション単位課金

LangChain・CrewAI・Claude MCPエコシステムはすでにx402ペイメントアダプターを標準搭載。エージェントが402レスポンスに当たると、自動的にウォレット残高を確認して支払います。

x402 = AIエージェントとAPIサービスの間に流れる配管。TCP/IPと同じ。

exactスキームの限界 → uptoによる解決

当初のexactスキームは、リクエスト前に金額を確定させる必要があった。しかしLLM推論・帯域幅課金・GPU使用時間など、AIインフラのコストは実行完了後にしか確定しない。

2026年4月に導入されたuptoスキームはこの制約を解消する。クライアントが事前に「上限額」にオフチェーン署名（ガスコストゼロ）し、サービス完了後にサーバーが実使用量ベースの金額のみを決済する。Permit2コントラクトが上限超過を技術的に不可能にする。

例: エージェントが最大$5.00を承認 → サーバーが$0.42のみ決済（21,000トークン消費ベース）

エスクロー方式と異なり、決済まで資金はウォレットに留まり流動性が維持される。並列APIコールが多いほど、この優位性が大きくなる。

uptoスキームの詳細 →

MPPのSessionモード：LLMトークン課金に対応

MPPはChargeモード（1リクエスト1決済）に加え、Sessionモードを持つ。事前デポジット後はオフチェーンの署名済みバウチャーを提示するだけで決済が完結し、レイテンシはほぼゼロになる。LLMのトークン単位課金や、AIが複数APIを連続して叩くワークフローに特に有効だ。

Hono + MPP 
// Honoでの実装例（MPP）
import { paymentMiddleware } from 'mppx/hono';

app.get('/premium-data',
  paymentMiddleware({ price: '$0.01', currency: 'USD' }),
  async (c) => c.json({ data: 'paid by AI agent' })
);

x402 Foundation

2025年4月2日、x402 FoundationがLinux Foundation傘下のオープンガバナンス組織として正式に発足しました。単一の企業がx402標準を所有・支配することはありません。すべての人が読み、構築し、貢献できます。

インターネットのインフラ層（HTTP・SMTP・TCP/IP）がオープン標準として世界を変えたように、AIエージェント時代の決済レイヤーもオープンであることが期待されます。

なぜオープン標準が勝つのか

HTTP vs. AOL

AOLは3000万人のインターネットでしたが、クローズドなガーデンでした。HTTPはオープンなプロトコルで、誰でも構築できました。AOLは今や歴史の注釈に過ぎませんが、HTTPはウェブそのものです。

TCP/IP vs. OSI

「公式」ネットワーク標準（OSI）は、完璧さよりも広く採用されたオープン版に敗れました。標準への合意は完璧な標準よりも多くの価値を生みます。

1つの企業がエージェントのトランザクション層を支配する代わりに—x402はその代替を提供します。誰でも参加でき、誰も締め出されない。

x402 と MPP の関係

x402

HTTP 402 × Web3の文脈で生まれ、ブロックチェーン上のUSDC決済にフォーカス。Linux Foundation傘下のオープンスタンダード。

MPP

x402の思想を継承しつつ、Stripe（カード）・Tempo（ステーブルコイン）・Lightning（BTC）を1つのインターフェースで統合。IETFにドラフト提出済み。後発なだけあってより広範な決済レールをカバーする。

→ StripeはMPPとx402の両方をサポートしている。レイヤーが違うだけで、どちらも公共財だ。

MPP吸収リスクとLinux Foundation独立性

MPPがx402を完全に吸収するシナリオはゼロではありません。StripeとTempoがMPPにx402の機能を全部取り込んで「x402は不要」になる可能性はあります。ただし、Linux Foundation傘下のオープンスタンダードという性質上、特定プラットフォームに依存したくない開発者がx402を選び続ける理由は残ります。HTTPがAOLに勝ったように、オープンな標準は長期的に生き残りやすい。

x402が普及する3つの経路

01

Stripe両対応

StripeはMPPとx402をどちらも統合。クリプトを知らない加盟店がx402対応APIのセラーになれる経路が開かれます。

03

AIエージェントが強制普及

LangChain・CrewAI・Claude MCPはすでにx402アダプターを標準搭載。エージェントが普及するほどx402対応APIへの需要が増え、開発者は「対応しないと売れない」状況になっていきます。
